## 1. 先确定全场唯一主线

项目不是“又一个相册”，而是一个**会随时间产生回报的共同生活档案**：

> 用 Moment 留下此刻，用 Chapter 组织一段生活，用 Perspective 保存同一经历的不同视角，最后通过 Calendar、Review 和 Memory Echo 重新看见它。

全场只让观众记住三件事：

1. **低门槛记录**：先留下一句话、一张照片或一段声音，Chapter 归属可以以后再决定。
2. **同一瞬间，多人视角**：每个人的文字、照片、声音和署名独立保存，不覆盖原作者。
3. **时间产生回报**：记录可按日期、章节和时间关系重新阅读，并形成回望海报。

### PPT 与 Demo 的分工

为避免重复，两个部分严格分工：

| 部分        | 重点                                                         | 不做什么                                  |
| ----------- | ------------------------------------------------------------ | ----------------------------------------- |
| PPT         | 产品定位、真实架构、时间回报、问题解决、研发体会             | 不逐步展示邀请和共同编辑                  |
| 双视角 Demo | A 发起邀请、B 加入并补充视角、A 看到结果、B 只能编辑自己内容 | 不演示 Calendar、Memory Echo、Review 海报 |

因此，Demo 是“协作能力的证据”，PPT 的功能高光是“时间价值”。两者互补，不重复。

### 可以有证据地讲的能力

- 原生微信小程序：WXML、WXSS、JavaScript，使用自定义组件和三入口导航。
- Moment：文字、照片、录音、地点、标签、日期、草稿、收藏和详情。
- Chapter：创建、编辑、进行中/完成/归档生命周期，以及瞬间、日历、回望。
- Perspective：同一 Moment 下的独立共同视角和评论，作者只能编辑自己的内容。
- 本地优先：记录先落本地 Storage，图片和声音通过 `wx.saveFile` 持久化，再进入待同步队列。
- 云端协作：`services/collaboration.js` 调用 `collaboration` 云函数；云函数读取真实 OPENID，并校验邀请范围、成员关系和内容所有权。
- 回望：按真实日期聚合记录，Canvas 生成 3:4 海报。
- Memory Echo：按往年同日、约 30/90/180 天前或 Chapter 第一刻带回旧记录；没有合适内容就隐藏。
- 搜索与个人档案：可搜索 Chapter、Moment、地点和标签，统计真实记录日、共同记录和开始日期。

### 汇报中必须保守表述的边界

- 当前源码具备云协作链路，但交接文档明确写着：**最新云函数部署和真实双账号真机验收尚未确认**。
- 因此未完成真机验收前，不说“已经在线稳定运行”，应说“云端代码和隔离账号模拟已完成，真实双账号是最后验收项”。
- 不说“实时同步”，当前机制是保存后同步、回到前台、定时或下拉刷新。
- 不说“AI 推荐”，Memory Echo 是明确的日期规则。
- 不说“所有测试通过”。2026-09-19 实际检查为：WXML 21 个模板、WXSS 22 个样式表编译通过；10 组 Node 检查中 6 组通过、4 组断言失败，失败涉及旧缓存迁移、设计规范、横滑间距和交互数据隔离。

## 3. 实际项目框架

### 用户可理解的产品结构

```text
Moment 此刻 ──归类──> Chapter 一段生活 ──积累──> Calendar / Review / Memory Echo
     │
     └── Perspective：朋友为同一瞬间留下自己的视角
```

### 技术架构图（第 3 页照此绘制）

```text
┌──────────────────────────────────────┐
│ 原生微信小程序                        │
│ Pages + Components                    │
│ WXML / WXSS / JavaScript              │
└───────────────┬──────────────────────┘
                ↓
┌──────────────────────────────────────┐
│ services/store.js 统一业务数据层       │
│ 数据规范化 / 权限判断 / 页面 Selector  │
└────────┬─────────────────┬───────────┘
         ↓                 ↓
┌────────────────┐  ┌──────────────────┐
│ 本地 Storage    │  │ collaboration.js │
│ 记录 / 草稿     │  │ 同步 / 重试 / 媒体 │
│ pendingOps 队列 │  └─────────┬────────┘
└────────────────┘            ↓
                    ┌──────────────────────┐
                    │ collaboration 云函数 │
                    │ OPENID / 邀请 / 权限  │
                    └─────────┬────────────┘
                              ↓
          ┌───────────────────┴─────────────────┐
          │ 云数据库：用户、章节、瞬间、视角、评论、邀请 │
          │ 云存储：照片与语音                         │
          └─────────────────────────────────────┘
```

架构页只讲三个结论：

1. 页面不直接散落读写缓存，而是统一经过 Store。
2. 保存先落本地，弱网时不丢操作，再由同步层补传。
3. 云函数根据 OPENID 校验“谁能看、谁能改”，共同视角是独立记录，不覆盖原文。

### 源码结构（答辩追问备用）

```text
app.js / app.wxss                启动、云环境、全局视觉令牌
components/                      导航、Chapter、Moment、Perspective 等复用组件
pages/                           当下、生活、详情、编辑、日历、回望、搜索、我的
services/store.js                本地状态、迁移、权限、统计、日期聚合
services/collaboration.js        云调用、上传、同步队列与刷新合并
services/review-poster.js        Canvas 海报
cloudfunctions/collaboration/    OPENID、邀请、读写和服务端权限校验
data/demo.js                     课程展示数据
tests/                           数据、权限、同步、海报、响应式和静态检查
```

### 第 1 页｜这个夏天，你还记得哪一刻？（20 秒）

**页面只放：**

- 大标题：这个夏天，你还记得哪一刻？
- 项目名：`ongoing_ / 未完`
- 一句话：把此刻，留成一段生活。
- 一张大幅夏日照片；右下角叠一条真实 Moment 的日期和一句话。
- 姓名、学号、个人项目、微信小程序。

**讲稿：**

> 手机里有很多照片，但过一段时间，我们常常忘了当时说过什么、和谁在一起。我的项目叫 ongoing_，中文名“未完”。它想把照片、当时的一句话，以及朋友眼中的同一刻放在一起，让零散内容慢慢成为一段可以重新阅读的生活。

### 第 2 页｜把零散记录，变成一段生活（35 秒）

**页面主体：**只画产品关系，不放具体功能截图。

```text
Moment 留下此刻 → Chapter 组织生活 → 时间带来回望
          ↓
Perspective 保存不同人的视角
```

下方三句：

- 写一句、加照片、留声音；先记录，归类可选。
- Chapter 为一段生活提供上下文。
- 日历、回望和时间来信让内容重新出现。

**讲稿：**

> 产品的最小单位是 Moment，一句话、一张照片或一段声音都可以，先留下，再决定是否归类。Chapter 可以是一个暑假，也可以是一段旅行。朋友可以为同一条 Moment 增加自己的 Perspective。内容积累后，再通过日期、章节和时间关系重新阅读。它不是为了发布给所有人，而是为自己和共同经历的人留下完整上下文。

### 第 5 页｜时间，让记录产生第二次价值（40 秒）

**版式：一大两小。**

- 左侧 60%：Memory Echo 首页卡片，大字标注“约一个月前 / Chapter 第一刻”等真实原因。
- 右上：Calendar 有记录日期的圆点与选中日。
- 右下：个人生活档案统计，或 Review 的章节统计，不使用 Demo 中的共同视角画面。
- 页面结论：`今天留下此刻，以后重新看见自己的生活。`

**讲稿：**

> 这个项目真正想解决的，不只是“怎么记”，还有“以后为什么回来”。Memory Echo 会按真实日期，把往年同日、大约一个月前，或者某一章的第一刻重新带到今天，并说明它出现的原因。Calendar 让记录按天重新展开，生活档案则把 Moment 数、记录日和开始日期变成真实积累。没有符合条件的旧记录时，时间来信会直接隐藏，不用虚构内容填满界面。

`分享卡片受限 → 复制邀请文字 + 粘贴预览 → Chapter 与单条 Moment 范围明确`

第二行：

`多账号 + 弱网 + 修改冲突 → OPENID + 账号隔离 + pendingOps + 作者权限 → 不串号、不覆盖原文、失败可重试`

右下角放一个小状态框：

```text
已验证：模板/样式编译、协作模拟、云端权限、时间规则、海报
待完成：最新云函数部署、真实双账号与 iOS/Android 真机验收
```

**讲稿：**

> 开发中，第一个问题是体验环境的微信分享卡片受限。我没有把入口留成不可用状态，而是改为复制邀请文字、对方粘贴、云端预览后确认，并区分整章邀请和单条 Moment 邀请。第二个问题是多人数据的归属：换账号、断网或重复保存后，内容仍要属于正确的人。我使用云函数读取 OPENID，本地缓存和草稿按账号隔离，修改先进入持久化队列；服务端再检查作者和成员权限。当前编译与主要逻辑检查已完成，最新云端部署和双账号真机仍作为最后验收项。

### 第 7 页｜我学会了把一次操作，做成完整体验（30 秒）

**页面只放三个词组：**

- 工程闭环：保存、同步、身份、权限、再读取。
- 真实状态：空内容、草稿、弱网和失败都需要设计。

**讲稿：**

> 这次开发让我学到三件事：先通过产品取舍降低记录门槛；再把保存、同步、身份和权限串成完整流程；最后认真处理空状态、草稿和失败状态，而不只做理想路径。下一步是完成真实双账号和多机型验收。ongoing_ 想做到的，就是此刻很轻，时间会记得。谢谢大家。

## 5. 双视角 Demo：100 秒录屏脚本

### 最佳录法

- 画面为左右分屏：左侧 A（创建者），右侧 B（朋友）。两台真机或两个真实微信账号。
- 每侧顶部固定小标签 `A · 记录者`、`B · 朋友`，不要依赖观众辨认头像。
- 输入和网络等待剪掉或 2 倍速；结果页保持正常速度，确保老师看清。
- 视频不配完整旁白，现场讲；视频中只加短字幕和必要点击高亮。
- 总时长控制在 95—100 秒，宁可短 5 秒，不可超时。

### 分镜

| ------------ | ----------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------- | ------------------------------ |

| 00:12—00:25 | 点“邀请朋友留下视角”，复制邀请文字      | 等待                                                                                 | “邀请只授予这一条记录的访问和补充权限。”           | 单条 Moment 邀请，不扩大到整章 |
| 00:25—00:40 | 保持详情                                  | 粘贴邀请文字，看到邀请人、范围、封面后确认                                           | “B 先看到邀请范围，再决定加入。”                   | 云端预览与范围清晰             |

### 演示前必须准备

1. 部署当前 `collaboration` 云函数，并确认六个集合存在：users、chapters、moments、contributions、comments、invites。
2. A、B 都加入最新体验版，并在“我的”设置易区分昵称和头像。
3. A 准备一条**不属于 Chapter** 的日落 Moment，避免邀请范围解释复杂。
4. 两个账号先完整走通一次，再重新创建一条正式录屏用 Moment。
5. 录制前打开稳定网络，关闭消息通知，统一屏幕亮度。
6. 录制后检查：B 的 Contribution 在云端作者为 B；A 原 Moment 作者仍为 A。

## 8. PPT 视觉设计规则

- 比例：16:9，浅米白底；主色使用项目的鼠尾草绿，杏色和淡紫只作强调。
- 字体：中文使用思源黑体/苹方/微软雅黑之一；英文用同一无衬线体系，避免临时安装字体导致换机错位。
- 每页只保留一个结论；标题 30—36 pt，正文不低于 18 pt。
- 不做“九宫格功能大全”，不展示代码截图墙，不放超过 6 行的段落。
- 架构图用 6 个以内的大模块，箭头体现真实数据方向。
- 只有第 4 页播放视频；其他页不放 GIF，避免共享窗口掉帧。
- 页码旁固定一条极短章节词：`WHY / PRODUCT / ARCHITECTURE / DEMO / VALUE / PROBLEM / LEARNING`。

## 10. 老师可能追问的简短回答

**为什么不用朋友圈或普通相册？**
朋友圈强调发布，相册强调文件；ongoing_ 强调一段生活的上下文、多人不同视角和长期回看。

**为什么先存本地？**
生活记录常发生在弱网场景。本地先保存能降低丢失风险，pendingOps 再补传，但仍会把同步失败明确告诉用户。

**怎么保证别人不能改我的内容？**
客户端隐藏无权操作，服务端仍以 OPENID、成员关系和 creatorId 做最终校验；共同视角是独立记录。

**Memory Echo 是 AI 吗？**
不是。它使用可解释的日期窗口和 Chapter 第一刻规则，且没有符合条件的内容时不展示。

**目前最大的未完成项是什么？**
最新云函数部署后的真实双账号、断网恢复和 iOS/Android 真机兼容验收。
